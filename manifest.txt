--------------------------------------------------------------------------------
 1. ZWECK
--------------------------------------------------------------------------------
Der Patcher uebertraegt Aenderungen an einem Projekt (Quellcode, Skripte,
Konfigurationsdateien, langfristig beliebige Sprachen und Formate) mit einer
einzelnen Patchdatei in eine andere Umgebung. Statt ganze Dateien zu
kopieren oder auszutauschen, enthaelt die Patchdatei nur die Aenderungen -
auf Wunsch feingranular bis auf einzelne Funktionen, Methoden, Klassen oder
Abschnitte.

Kernanforderungen:
  A1  Aenderungen nur ueber Patchdateien (keine Handarbeit am Zielprojekt).
  A2  Hash-Pruefung auf Dateiebene UND fuer jede einzelne Aenderung
      innerhalb der Datei (Funktion, Methode, Klasse, Header, Textblock).
  A3  Befehle der Art: "aendere in Datei X die Funktion Y von Z nach Z'".
  A4  Jeder angewendete Patch kann vollstaendig zurueckgenommen werden
      (Rollback auf den vorherigen Stand).
  A5  Ein Patch wird ganz oder gar nicht angewendet (atomar).
  A6  Abweichungen vom erwarteten Stand werden erkannt und fuehren zum
      Abbruch, bevor etwas veraendert wird.
  A7  Erweiterbar auf weitere Sprachen/Formate ueber Adapter (Abschnitt 8).
  A8  Die Pruefung bewertet die FUNKTION, nicht die Schreibweise:
      Kommentare und unwichtige Leerzeichen/Tabs/Umbrueche fliessen je
      nach Format nicht in den Hash ein (Normalform, Abschnitt 5).
  A9  Der Patcher veraendert niemals die Funktion von Code durch
      Umformatierung. Er formatiert nichts um; die Normalform dient
      ausschliesslich der Hash-Berechnung.
  A10 Die PATCHDATEI legt je Datei fest, wie verglichen wird (Vergleichs-
      profil: raw, text, python, ...; Kommentare ja/nein, Leerraum ja/nein,
      binaer gleich ...). Abschnitt 5.2.


--------------------------------------------------------------------------------
 2. ENTSCHEIDUNGEN (geklaerte Punkte)
--------------------------------------------------------------------------------
  E1  Sprachen: langfristig alle Sprachen und Formate, umgesetzt nach Bedarf
      ueber Adapter. Erste Version: Python-, Text- und Raw-Behandlung.
  E2  Patchformat: Befehlsliste + Datenbloecke als Text (pypatcher/1,
      Abschnitt 6); ersetzt in der Testphase das anfaengliche JSON.
  E3  Pruefung grundsaetzlich auf Dateiebene. Alle Aenderungen an einer
      Datei werden im Patch unter dieser Datei gesammelt; jede einzelne
      Aenderung wird ebenfalls per Hash geprueft (Pruefkette, Abschn. 4.5).
  E4  Kommentare direkt ueber einer Funktion/Klasse gehoeren raeumlich zur
      Einheit (sie wandern mit). Der Kopf der Datei ist eine eigene
      Einheit "@header" (Abschnitt 7.3).
  E5  Funktion vor Schreibweise: Gepruefte Hashes werden ueber eine
      formatabhaengige Normalform gebildet. Kommentare sind der Funktion
      untergeordnet und fliessen standardmaessig nicht ein; ebenso nicht
      unwichtige Leerzeichen, Tabs und Umbrueche (je nach Format).
  E6  Zielumgebung kann Windows/CRLF sein: Zeilenenden werden erkannt
      und beim Schreiben beibehalten. "doctor" prueft vorab die Umgebung.
  E7  Eigenes, privates Repository "pypatcher".
  E8  Signatur: vorgesehen (spaeter als zusaetzliche Kopfangabe),
      zunaechst nicht umgesetzt.
  E9  Binaerdateien: ueber mode "raw" (Base64, nur ganze Datei).
  E10 Versionierung: waehrend der Konzeptphase keine Versionsnummern.
      Erste Version 0.0.1; bis zur Freigabe als 0.0.1-pre1, -pre2, ...
      (Abschnitt 16).
  E11 Docstrings sind programmrelevant (z.B. __doc__, argparse-Hilfe) und
      zaehlen deshalb standardmaessig zur Funktion. Ignorieren nur, wenn
      es im Vergleichsprofil ausdruecklich festgelegt ist.
  E12 Vergleichsprofil je Datei in der Patchdatei (A10, Abschnitt 5.2).
  E13 Python: Einrueckung ist Teil der Funktion. Tiefe UND Zusammensetzung
      (Anzahl Leerzeichen, Tabs, Mischung) jeder Anweisungszeile werden
      exakt geprueft - nicht abschaltbar. Bei Sprachen, in denen die
      Einrueckung keine Bedeutung hat (js, c/c++ ...), wird sie ignoriert.
  E14 Einrueckung im Patch: fuehrende Tabs geben die RELATIVE Ebene an
      ("\t\treturn x" = 2 Ebenen tiefer als die Einheit/der Block selbst).
      Grundtiefe und Ebenen-Einheit (Tab, 4 Leerzeichen ...) ergeben sich
      beim Anwenden aus dem Text der Zieldatei. Der Parameter layout (ind=)
      ist optional und dient als zusaetzlicher Check (Abschnitt 6.1).
  E15 Bearbeiten innerhalb von Einheiten: replace_text/insert_text/
      delete_text mit optionalem "scope" (Abschnitt 7.1).
  E16 Kopieren und Verschieben von Dateien und Einheiten (copy/move),
      auch zwischen Dateien (Abschnitt 7.4).
  E17 Umfang 0.0.1 und spaeter: Abschnitt 13.
  E18 Pruefstufen waehlbar (min/std/full): nur Datei, zusaetzlich
      Funktionen, oder alles - so sicher und informativ wie gewuenscht;
      Hash-Laenge einstellbar (Abschnitt 6.6).
  E19 Kein alter Code im Patch, ausser als Suchtext fuer Textaenderungen;
      Rollback ueber die Sicherung im Ziel; Patches von Version zu Version.
  E20 Pakete mit begrenzter Zeichenzahl optional (--max-size, 6.2).
  E21 Web-Formate in der Reihenfolge JS -> CSS (inkl. verschachtelt,
      SCSS/LESS) -> HTML/XML; TypeScript/JSX danach. HTML-Adressen
      robust (id, Tag + Klassen + Nummer) statt kurz; HTML-Leerraum
      zaehlt standardmaessig; <script>/<style> sind ganze Einheiten
      ("Sicherheit vor Sparsamkeit"). Abschnitte 5.6, 7.2.
  E22 Ablaufsteuerung im Patch (PRINT, INPUT, IF/ELIF/ELSE/END,
      LABEL/GOTO, SET, EXIT): Entscheidungen werden beim Anwenden
      abgefragt statt von Hand nachgearbeitet (6.8).
  E23 KI-Nutzung: eine KI im Chat schreibt Entwuerfe (ohne Hashes), auch
      ueber mehrere Nachrichten; "run" prueft sie gegen das Zielprojekt
      und wendet sie an. Prompt: ki-prompt.txt (6.9).
  E24 TypeScript/JSX (R016) hinten angestellt.
  E25 Komprimierung optional (--compress): nur die Datenbloecke, gemeinsam
      (zlib + Base64); die Befehlsliste bleibt lesbar (6.10). Ziel sind
      Zeichengrenzen bei der Uebertragung - Tokens spart Base64 kaum.
  E26 Offen fuer Erweiterungen: Patches nennen genutzte Funktionen
      (USES); Versionen ohne diese Funktion brechen mit klarer Meldung ab
      statt falsch zu lesen (6.3). Gleiches gilt fuer unbekannte
      Block-Kodierungen.
  E27 KI mit Werkzeugen nutzt pypatcher selbst (patcher.pyz): prueft,
      versiegelt und liefert den Patch als Datei (6.9, ki-prompt.txt).
  E28 Viele Sprachen und Datenformate: zusaetzlich C/C++ (Grundlage fuer
      weitere Sprachen der C-Familie) und JSON (5.6.4, 5.6.5).

 3. BEGRIFFE
--------------------------------------------------------------------------------
Projekt        Verzeichnisbaum, der gepatcht wird (Projektwurzel).
Patch          Eine Patchdatei (*.ppatch), ggf. in Pakete geteilt.
Dateieintrag   Alle Aenderungen eines Patches an EINER Datei.
Aenderung      Einzelner Schritt innerhalb eines Dateieintrags
               (z.B. replace_unit).
Einheit (Unit) Adressierbarer Abschnitt einer Datei, z.B. Funktion
               "parse_cue", Methode "Converter.run" oder "@header".
Adapter        Sprach-/Formatmodul: findet Einheiten, bildet die Normalform,
               setzt Einheiten ein (python, text, raw, spaeter js, c ...).
Vergleichs-    Festlegung in der Patchdatei, WIE eine Datei verglichen
profil         wird (mode + Optionen). Abschnitt 5.2.
Normalform     Darstellung eines Inhalts gemaess Vergleichsprofil; enthaelt
               nur, was laut Profil zaehlt. Grundlage des Funktions-Hashes.
Funktions-Hash Hash ueber die Normalform ("hash"). Wird geprueft.
Text-Hash      Hash ueber den exakten Text (nur Zeilenenden vereinheitlicht)
               ("text_hash"). Wird protokolliert, nur auf Wunsch geprueft.
Hash           SHA-256, notiert als "sha256:<64 hex-zeichen>".
Zustand        Gesamtheit aller Datei-Hashes des Projekts.
Journal        Verwaltungsverzeichnis ".patcher/" in der Projektwurzel.
Entwurf        Patch ohne Hashes/Altinhalte, von Hand geschrieben;
               wird mit "seal" zu einem vollstaendigen Patch.


--------------------------------------------------------------------------------
 4. HASH-KONZEPT
--------------------------------------------------------------------------------
4.1 Algorithmus
  SHA-256 (hashlib). Schreibweise "sha256:..." damit spaeter weitere
  Algorithmen moeglich sind, ohne das Format zu brechen.

4.2 Zwei Hash-Arten
  hash       Funktions-Hash: SHA-256 ueber die Normalform gemaess
             Vergleichsprofil (Abschnitt 5). Wird bei apply/check/rollback
             immer geprueft. Bei mode "raw" = SHA-256 der rohen Bytes.
  text_hash  Text-Hash: SHA-256 ueber den Text nach Entfernen des BOM
             und Vereinheitlichen der Zeilenenden auf LF. Aendert sich
             bei jeder Aenderung, auch an Kommentaren/Leerzeichen.
             Wird protokolliert (Journal) und meldet kosmetische
             Abweichungen als Hinweis. Mit --exact wird er zusaetzlich
             streng geprueft.
  In die Hash-Berechnung fliesst die Profil-Kennung mit ein (Abschnitt
  5.2), damit gleiche Inhalte mit verschiedenen Profilen nie
  verwechselt werden.

4.3 Datei-Hash und Einheiten-Hash
  Datei   : hash/text_hash ueber die gesamte Datei.
  Einheit : hash/text_hash ueber die Einheit (Umfang: Abschnitt 7.3).
            Python: die absolute Einrueckung jeder Anweisungszeile der
            Einheit zaehlt mit (E13). Formate ohne bedeutsame
            Einrueckung: Einrueckung zaehlt nicht.

4.4 Zustands-Hash (Projekt)
  SHA-256 ueber die sortierte Liste "relativer_pfad\0hash\n" aller
  verwalteten Dateien. Ignoriert werden ".patcher/", die Vorgaben
  .git, __pycache__, *.pyc, .DS_Store, Thumbs.db, desktop.ini, *.ppatch,
  Muster aus config.json ("ignore") und aus ".patcherignore" (eine
  fnmatch-Maske je Zeile, # = Kommentar). "!muster" nimmt eine Vorgabe
  zurueck (z.B. "!*.ppatch", wenn Patchdateien zum Projekt gehoeren).
  .patcherignore selbst wird nie verwaltet: die Ignore-Regeln gehoeren
  zur jeweiligen Umgebung und werden nicht per Patch uebertragen.
  Ignore-Regeln gelten immer in ihrer aktuellen Fassung: eine verwaltete
  Datei, die neu ignoriert wird, faellt aus der Verwaltung (verify:
  Hinweis); eine nicht mehr ignorierte Datei ist "neu, nicht verwaltet"
  und wird per Patch (REP) oder - ohne angewendete Patches - mit
  "init --force" aufgenommen.
  Profil je Datei fuer den Zustands-Hash: vom Patch beruehrte Dateien
  mit dem Profil aus dem Patch, alle anderen automatisch (Binaerdatei ->
  raw, *.py und parsebar -> python, sonst text).
  Dieselbe Regel gilt beim Versiegeln (seal, create, run mit Entwurf;
  0.0.2): ist die vorhandene Datei im Format ihrer Endung ungueltig (z.B.
  .py mit Syntaxfehler) und gibt der Patch kein Profil vor, wird sie als
  text behandelt (Hinweis). So laesst sie sich mit REP/TEXT reparieren;
  Einheiten-Befehle brauchen weiterhin eine gueltige Datei.

4.5 Pruefkette innerhalb einer Datei
  Welche Hashes ein Patch enthaelt, bestimmt die Pruefstufe (6.6).
  Vollstaendig (full): jeder Dateieintrag hat hash_before und hash_after
  der ganzen Datei, jede Aenderung im Eintrag zusaetzlich:
    unit_hash_before / unit_hash_after   - Hash der Einheit
    file_hash_before / file_hash_after   - Zwischenstand der Datei
  Die Aenderungen bilden eine Kette:
    Datei.hash_before == Aenderung[1].file_hash_before
    Aenderung[n].file_hash_after == Aenderung[n+1].file_hash_before
    Aenderung[letzte].file_hash_after == Datei.hash_after
  Beim Anwenden (alles zuerst im Speicher), soweit im Patch enthalten:
    VOR jeder Aenderung  : Datei-Zwischen-Hash und Unit-Hash pruefen
    NACH jeder Aenderung : Unit-Hash und Datei-Zwischen-Hash pruefen
  Stimmt ein Hash nicht -> Konflikt mit genauer Angabe (Datei, Aenderung,
  Einheit, erwartet/gefunden), nichts wird geschrieben.

4.6 Pruefmodus (Umfang)
  --match file  (Standard): Funktions-Hashes von Datei und Einheiten.
  --match state           : zusaetzlich gesamter Projektzustand
                            (state_before) muss stimmen.
  --match unit            : nur Unit-Hashes; die Datei darf an anderer
                            Stelle funktional abweichen (Notfall, muss
                            ausdruecklich angegeben werden).
  --exact                 : zusaetzlich Text-Hashes (Kommentare und
                            Leerzeichen muessen exakt stimmen).
  WIE streng verglichen wird, bestimmt das Vergleichsprofil in der
  Patchdatei; die Optionen hier koennen nur verschaerfen, nie lockern.

4.7 Patch-Hash (Integritaet der Patchdatei)
  SHA-256 ueber den gesamten Inhalt der Patchdatei ohne Kopfzeile, bei
  Paketen zusaetzlich ein Hash je Paket (Abschnitt 6.2). Erkennt
  beschaedigte oder veraenderte Patchdateien (inkl. veraenderter
  Profile). Falscher Patch-Hash -> Patch wird abgelehnt.

4.8 Signatur (vorgesehen, zunaechst nicht umgesetzt)
  Spaeter als zusaetzliche Kopfangabe ueber denselben Inhalt wie der
  Patch-Hash; moegliche Verfahren HMAC-SHA256 oder Ed25519 (request.txt).


--------------------------------------------------------------------------------
 5. VERGLEICHSPROFIL UND NORMALFORM
--------------------------------------------------------------------------------
5.1 Grundsaetze
  N1  Die Normalform enthaelt alles, was laut Vergleichsprofil zaehlt,
      und nichts anderes.
  N2  Kommentare fliessen standardmaessig nicht ein (der Funktion
      untergeordnet) - ausser das Profil verlangt es ("comments": "keep").
  N3  Leerzeichen, Tabs und Umbrueche fliessen nur ein, wenn sie im
      jeweiligen Format Bedeutung haben (Python-Einrueckung, YAML-
      Einrueckung, Tabs in Makefiles, Inhalt von Zeichenketten) oder das
      Profil es verlangt ("whitespace": "keep").
  N4  Inhalte von Zeichenketten bleiben immer unveraendert.
  N5  Im Zweifel gilt etwas als funktional (lieber eine Abweichung zu
      viel melden als eine echte Aenderung uebersehen).
  N6  Jede Normalform hat eine Version ("python/1"). Eine Aenderung der
      Regeln ergibt eine neue Version; alte Patches bleiben pruefbar.
  N7  Die Normalform ist unabhaengig von Betriebssystem, Zeilenenden
      (ausser mode "raw"), Encoding/BOM und Python-Version des Patchers.

5.2 Vergleichsprofil in der Patchdatei
  Festgelegt im Patch fuer jede Datei (Profil-Kurzform, Abschnitt 6.4).
  Rangfolge:
    1. Profil am Dateibefehl (z.B. "FILE x.py py,comments=keep")
    2. DEFAULT im Patchkopf (gilt fuer alle Dateien des Patches)
    3. eingebaute Vorgabe je Dateiendung (*.py -> python, sonst text)
  Beim Anwenden ist allein das Profil im Patch massgeblich (der Patch
  wurde damit gehasht). ".patcher/config.json" bestimmt nur die
  Vorgaben fuer create/seal und kann Mindestprofile erzwingen
  (z.B. "*.cfg muss raw sein") - ein Patch mit schwaecherem Profil wird
  dann abgelehnt.

  Felder:
    mode        raw | text | python   (spaeter js, cpp, c, java, shell,
                json, yaml, ini, xml, markdown, make ...)
    comments    ignore | keep         Kommentare im Hash?
    whitespace  ignore | keep         unwichtiger Leerraum im Hash?
                                      (bedeutsamer Leerraum zaehlt immer)
    docstrings  keep | ignore         nur python (E11)
    indent      exact | ignore        python: immer exact (E13, fest);
                                      js/c/...: Vorgabe ignore
    eol         normalize | keep      keep = Zeilenenden zaehlen mit
    encoding    utf-8 | latin-1 | ... Dekodierung fuer Textmodi

  Beispiel (Kurzform im Patch, nur Abweichungen von den Vorgaben):
    py                        = python mit allen Vorgaben
    py,comments=keep          = Kommentare zaehlen mit
    txt,whitespace=keep       = Text exakt inkl. Leerzeichen am Zeilenende

  Unzulaessige Kombinationen (z.B. python mit indent=ignore, raw mit
  comments=ignore) -> Patch ungueltig.

  Profil-Kennung: aus mode, Normalform-Version und allen Optionen wird
  eine eindeutige Kennung gebildet, z.B.
    "python/1;comments=ignore;docstrings=keep;eol=normalize;
     indent=exact;whitespace=ignore"
  Sie ist der erste Teil der Hash-Eingabe (4.2).

5.3 mode "raw" - binaer gleich
  Hash ueber die rohen Bytes, keinerlei Normalisierung (auch nicht
  Zeilenenden/BOM). Nur ganze Datei (add/delete/replace) und
  replace_text auf Byte-Ebene. Geschrieben werden exakt die Bytes aus dem
  Patch; Zeilenenden werden NICHT an die Zieldatei angepasst.

5.4 mode "text" - allgemeine Textdatei
  Da Kommentarzeichen und Bedeutung von Leerraum unbekannt sind, gilt
  vorsichtig (N5):
    whitespace=ignore : nur Leerzeichen/Tabs am Zeilenende und
                        Leerzeilen am Dateiende ignoriert
    whitespace=keep   : exakter Text
    comments=ignore   : nur moeglich mit Zusatzangabe "comment_prefix"
                        (z.B. "#"); dann werden reine Kommentarzeilen
                        ignoriert. Ohne Angabe zaehlen Kommentare.
  Einrueckung und Leerzeilen im Text bleiben immer funktional.

5.5 mode "python" - Normalform python/1
  Die Normalform besteht aus zwei Teilen:
  a) Syntaxbaum (Modul ast). Damit ohne Bedeutung: Kommentare,
     Leerzeilen, Leerzeichen innerhalb von Zeilen, Zeilenumbrueche in
     Klammern, Backslash-Fortsetzungen, Klammerung ohne Wirkung,
     Anfuehrungszeichen-Art ('a' == "a"), Zahlenschreibweise
     (0x10 == 16), Zeichenketten-Verkettung ("a" "b" == "ab").
     Funktional: alle Anweisungen/Ausdruecke, Namen, Werte,
     Reihenfolge, Decorators, Docstrings (E11, ausser docstrings=ignore).
  b) Einrueckungs-Signatur (E13). Fuer jede Anweisungszeile (jede
     Anweisung, die am Zeilenanfang beginnt, inkl. def/class/if/for/
     return ...) wird der exakte Einrueckungs-Text vor der Anweisung
     erfasst, z.B. "    " (4 Leerzeichen), "\t", "\t    ".
     Damit zaehlen Tiefe UND Zusammensetzung. Nicht erfasst:
     Fortsetzungszeilen innerhalb von Klammern, Kommentar- und
     Leerzeilen (dort ist Einrueckung ohne Bedeutung).
     Beispiele (Prototyp geprueft):
       anderer Kommentar / Leerzeile / (1) statt 1  -> gleicher Hash
       Tab statt 4 Leerzeichen                      -> anderer Hash
       8 statt 4 Leerzeichen Einrueckung            -> anderer Hash
       return 2 statt return 1                      -> anderer Hash
  Zusaetzlich funktional (nur Datei und @header): Shebang-Zeile und
  Encoding-Zeile (bestimmen Interpreter bzw. Dekodierung).
  comments=keep / whitespace=keep: die Normalform ist dann der exakte
  Text (wie mode text mit whitespace=keep), Einheiten bleiben nutzbar.
  Serialisierung des Syntaxbaums (eigene, versionsfeste Ausgabe statt
  ast.dump, da sich ast.dump zwischen Python-Versionen unterscheidet):
    - Knoten: Typname(feld=wert,...) in fester Feldreihenfolge
    - Felder mit None oder leerer Liste werden weggelassen
    - ignoriert: Positionsangaben, ctx, type_comment, kind
    - versionsbedingte Knoten werden vereinheitlicht (z.B. Index/
      ExtSlice aus Python 3.8 -> Form ab 3.9)
    - Konstanten mit Typkennung: str/bytes/int/float/complex/bool/None
    - f-Strings: leere Textteile entfallen, benachbarte Textteile werden
      zusammengefasst (Python 3.12 erzeugt sonst abweichende Baeume)
    Gepruefte Stabilitaet: identischer Hash auf Python 3.8, 3.11, 3.12
    und 3.13 (Referenzwert in tests/test_normalform.py).
  Laesst sich eine Datei nicht parsen (Syntaxfehler), wird sie
  abgelehnt; ein Patch kann fuer diese Datei mode "text" festlegen.

5.6 Weitere Modi (Web-Formate)
  Einrueckung hat in diesen Formaten keine Bedeutung und zaehlt nicht;
  es gibt daher keine Option indent. whitespace=keep / comments=keep
  verschaerfen wie bei python.

5.6.1 mode "js" - Normalform js/1 (umgesetzt)
  Dateien *.js, *.mjs, *.cjs. Eigener Tokenizer (Standardbibliothek).
  - Kommentare, Einrueckung und Leerraum zwischen Tokens zaehlen nicht.
  - Zeichenketten, Template-Strings (inkl. ${...}) und regulaere
    Ausdruecke bleiben exakt ('a' und "a" gelten als verschieden -
    lieber eine Abweichung zu viel, N5).
  - Zeilenumbrueche zaehlen nur, wo sie wegen der automatischen
    Semikolon-Einfuegung (ASI) die Bedeutung aendern koennen: nach
    return/throw/break/continue/yield/async und vor ( [ + - / ++ -- `
    * . ?. , = => sowie vor Template-Strings und regulaeren Ausdruecken.
    Umbrueche z.B. innerhalb einer Argumentliste zaehlen nicht.
  - Syntaxpruefung: Tokens gueltig (Zeichenketten, Kommentare, Templates
    geschlossen) und Klammern ausgeglichen. Keine vollstaendige
    Grammatikpruefung.
  - Ein "/" gilt als regulaerer Ausdruck nach Operatoren, oeffnenden
    Klammern und Woertern wie return/typeof; nach ) ] } als Division.

5.6.1a mode "ts", "tsx", "jsx" - Normalform js/1 (0.0.3)
  *.ts, *.mts, *.cts (ts), *.tsx (tsx), *.jsx (jsx). Tokenizer und
  Normalform wie js; Profil-Kennung ts/1, tsx/1, jsx/1.
  - JSX (tsx, jsx): ein Element bzw. Fragment (<>..</>) ist ein Token mit
    exaktem Text (Leerraum im JSX zaehlt); {..} darin wird wie Code
    gelesen. "<" leitet JSX nur dort ein, wo ein Ausdruck beginnt.
  - TypeScript-Syntax fuer Einheiten: Typ-Annotationen (auch Rueckgabe-
    typen mit Objekttyp), Generics <..>, Modifikatoren (public, private,
    protected, readonly, abstract, override, declare ...), optionale
    Mitglieder (name?), Dekoratoren (gehoeren zur Einheit).
  - Was der Tokenizer nicht lesen kann, wird wie bei init als text
    behandelt (Hinweis).

5.6.2 mode "css" und "scss" - Normalform css/1 (umgesetzt)
  css fuer *.css; scss fuer *.scss und *.less (zusaetzlich //-Kommentare,
  #{...}-Interpolation). Verschachtelte Regeln werden unterstuetzt
  (natives CSS-Nesting, SCSS/LESS).
  - Kommentare zaehlen nicht; Leerraum wird zu einem Leerzeichen
    zusammengefasst und entfaellt neben { } ; , sowie um den ersten ":"
    einer Deklaration. Leerraum in Selektoren bleibt (a :hover !=
    a:hover), ebenso in Werten (calc(1px + 2px)).
  - Ein ";" direkt vor "}" zaehlt nicht.
  - Reihenfolge der Regeln und Deklarationen zaehlt (Kaskade).
  - Zeichenketten und url(...) bleiben exakt.
  - Syntaxpruefung: Zeichenketten/Kommentare geschlossen, Bloecke
    ausgeglichen, kein Block ohne Selektor.

5.6.3 mode "html" und "xml" - Normalform html/1, xml/1 (umgesetzt)
  html fuer *.html, *.htm, *.xhtml (fehlertoleranter Parser der
  Standardbibliothek); xml fuer *.xml, *.svg, *.xsd, *.xsl (strenger
  Parser).
  - Kommentare zaehlen nicht.
  - Reihenfolge der Attribute und Art der Anfuehrungszeichen zaehlen
    nicht; Entitaeten werden aufgeloest (&amp; == &#38;).
  - Leerraum im Text zaehlt standardmaessig (whitespace=keep, "auf
    Nummer sicher"): CSS kann Leerraum sichtbar machen (white-space:
    pre). Auch Einrueckung zwischen Elementen zaehlt dann.
    whitespace=ignore (locker): Folgen werden zu einem Leerzeichen,
    Leerraum am Rand von Texten und reiner Leerraum zwischen Elementen
    zaehlt nicht - ausser in pre, textarea, script, style.
    Leerraum innerhalb von Tags (zwischen Attributen) zaehlt nie.
  - Inhalt von <script> (ohne type oder mit JS-type/module) und <style>
    wird mit der JS- bzw. CSS-Normalform verglichen; andere Skripttypen
    (z.B. JSON, Templates) exakt als Text.
  - DOCTYPE, XML-Deklaration und Verarbeitungsanweisungen zaehlen.
  - Syntaxpruefung: xml streng (expat); html ist fehlertolerant wie
    Browser, geprueft wird nur die Lesbarkeit.

5.6.4 mode "c" und "cpp" - Normalform c/1 (umgesetzt)
  c fuer *.c, *.h; cpp fuer *.cpp, *.cc, *.cxx, *.c++, *.hpp, *.hh, *.hxx,
  *.ipp, *.tpp. Eigener Tokenizer (Kommentare, Zeichenketten mit Praefix,
  Raw-Strings R"x(...)x", Zeichenliterale, Zahlen mit ' als Trenner,
  Praeprozessorzeilen inkl. Fortsetzung mit \).
  - Kommentare und Leerraum zaehlen nicht; Zeichenketten exakt.
  - Praeprozessorzeilen (#include, #define ...) zaehlen, ihr Leerraum ist
    vereinheitlicht; Kommentare darin zaehlen nicht.
  - Syntaxpruefung: Tokens gueltig, Klammern ausgeglichen (kein
    vollstaendiger Compiler-Parser).
  - Einheiten werden heuristisch erkannt; Zweifelsfaelle sind keine
    Einheit (dann Textbefehle).
  Gleiche Grundlage spaeter fuer Java, C#, Go, PHP, Rust (R023).

5.6.4a mode "java" - Normalform java/1 (0.0.3)
  *.java. Tokenizer der C-Familie ohne Praeprozessor, dazu "@"
  (Annotationen), Text-Bloecke """...""" (bleiben exakt) und >>>.
  Kommentare und Leerraum zaehlen nicht.

5.6.5 mode "json" - Normalform json/1 (umgesetzt)
  *.json, *.geojson, *.webmanifest. Normalform = die Daten selbst:
  - Formatierung zaehlt nicht; Reihenfolge der Schluessel standardmaessig
    auch nicht (aendert die Daten nicht) - mit keyorder=keep zaehlt sie.
  - Reihenfolge in Listen zaehlt; Zahlen behalten ihre Art (1 != 1.0);
    doppelte Schluessel bleiben erhalten.
  - Syntaxpruefung streng (wie json.loads); keine Kommentare (JSONC).
  - Kommas: nach Einfuegen/Loeschen/Ersetzen von Einheiten werden an den
    Grenzen fehlende Kommas ergaenzt und ueberzaehlige (vor } bzw. ])
    entfernt (repair) - nur dort, wo die Datei sonst ungueltig waere.

5.6.6 Spaeter (nach Bedarf, request.txt)
  cs, go, php, rust  auf Basis des C-Tokenizers (Java: 5.6.4a)
  shell             Kommentare entfernt, Leerraum zwischen Woertern
                    vereinheitlicht, Zeilenumbrueche bleiben
  yaml              parsen (Einrueckung funktional)
  ini               Abschnitte/Schluessel/Werte getrimmt, Kommentare weg
  make              Tabs am Zeilenanfang funktional

5.7 Was beim Schreiben passiert (A9)
  - Geschrieben wird exakt der Text aus dem Patch ("new"), nicht die
    Normalform.
  - Angepasst werden nur Zeilenenden/BOM/Encoding an die Zieldatei
    (nicht bei mode raw oder eol=keep).
  - Einrueckung: Die relativen Ebenen aus dem Patch werden an der
    Zielstelle in echte Einrueckung umgesetzt (Abschnitt 6.1/7.6): feste,
    verlustfreie Umrechnung mit Grundtiefe und Ebenen-Einheit aus der
    Zieldatei. Sonst wird nichts an der Einrueckung veraendert. Das
    Ergebnis wird ueber den Hash mit exakter Einrueckung (E13) geprueft.
  - Nach dem Einsetzen wird der Funktions-Hash erneut berechnet und mit
    dem erwarteten Wert verglichen; zusaetzlich validate (ast.parse).
  - Weicht die Zieldatei nur kosmetisch ab (gleicher hash, anderer
    text_hash), wird der Patch angewendet und ein Hinweis ausgegeben.
    Kommentare INNERHALB einer ersetzten Einheit werden durch die des
    Patches ersetzt; der vorherige exakte Text liegt im Journal und wird
    beim Rollback exakt wiederhergestellt.


--------------------------------------------------------------------------------
 6. PATCHDATEI-FORMAT pypatcher/1 (*.ppatch)
--------------------------------------------------------------------------------
Textdatei, UTF-8, eine Angabe pro Zeile - kompakt und ohne Escaping lesbar.
Aufbau:
  1. Kopfzeile (Kennung, Hashes)
  2. Kopfangaben (TITLE, DESC ...)
  3. Befehlsliste - wird von oben nach unten abgearbeitet
  4. Datenbloecke @1, @2 ... - Code/Text unveraendert, die Befehle
     verweisen darauf

Beispiel (Pruefstufe std):

  #PPATCH 1 0002-fix 9f2c41d07ab3e118
  TITLE check_overwrite fragt bei -a korrekt nach
  AUTHOR rs
  REQ 0001-basis
  FILE src/convert.py py h=aa11f0c2d9e4b7a1>ff9903e1c5a7b2d4 ind=4
    UNIT check_overwrite u=cc33a1b2c3d4e5f6>dd4401a2b3c4d5e6 @1
    TEXT scope=main u=0b1c2d3e4f5a6b7c>1c2d3e4f5a6b7c8d @2 @3
  REP data/logo.png raw h=5e6f7a8b9c0d1e2f>6f7a8b9c0d1e2f3a @4
  @1 3
  # Prueft, ob ueberschrieben werden darf
  def check_overwrite(path, force, ask):
  	return force or (ask and frage(path))
  @2 1
  if pruefen:
  @3 1
  if pruefen and not force:
  @4 2 b64
  iVBORw0KGgoAAAANSUhEUgAAAAEAAAABCAYAAAAfFcSJAAAADUlEQVR42mNk+M9QDwAD
  hgGAWjR9awAAAABJRU5ErkJggg==

6.1 Zeilen und Einrueckung
  Zeilen in Datenbloecken stehen mit RELATIVEN Ebenen: jeder fuehrende
  Tab = eine Ebene tiefer als die Grundtiefe des Blocks. Was nach den
  Ebenen-Tabs folgt, bleibt woertlich (z.B. Ausrichtung von
  Fortsetzungszeilen).
    Datei (Methode in Klasse, 4 Leerzeichen je Ebene):
      "    def f(self, a,"
      "              b):"
      "        return a"
    Patch (Grundtiefe = Tiefe der Methode, ergibt sich aus der Datei):
      "def f(self, a,"
      "\t\t  b):"             (2 Ebenen + 2 Leerzeichen)
      "\treturn a"
  Beim Anwenden ergibt sich aus dem Text der Zieldatei:
    - die Ebenen-Einheit (Tab, 4 Leerzeichen, 2 Leerzeichen ...)
    - die Grundtiefe: je Befehl aus der Zielstelle (Tabelle 7.6)
  Echte Zeile = Grundtiefe + Ebenen x Einheit + Rest woertlich.
  ind=4 / ind=tab (layout, optional, als Check):
    - weicht die erkannte Einheit der Zieldatei ab -> Konflikt
    - Pflicht nur, wenn sich die Einheit nicht aus dem Text ergibt
      (neue Datei, Datei ganz ohne Einrueckung)
    - seal/create tragen es ein (abschaltbar mit --no-layout)
  Block-Kennzeichen lit (Ausweichform): Zeilen stehen exakt wie in der
    Datei, keine Umrechnung; automatisch, wenn eine Zeile nicht relativ
    darstellbar ist (z.B. Tab in einer Datei mit Leerzeichen-Einrueckung).
  Die Umrechnung ist umkehrbar eindeutig; Hashes werden immer ueber den
  Text in Datei-Form berechnet (exakte Einrueckung, E13).
  Zum Lesen stellt "show" die Ebenen wie in der ungepatchten Datei dar
  (ind=...), oder wie mit --indent eingestellt.

6.2 Kopfzeile und Pakete
  Einteilig :  #PPATCH 1 <id> <patch-hash>
  Paket i/n :  #PPATCH 1 <id> <patch-hash> <i>/<n> <paket-hash>
  Entwurf   :  #PPATCH 1 <id>                  (ohne Hash: seal oder run)
  Entwurfsteil: #PPATCH 1 <id> <i>/<n|?>        (ohne Hash, 6.9)
  patch-hash = SHA-256 ueber den gesamten Inhalt ohne Kopfzeile(n), bei
  Paketen ueber die Inhalte in Reihenfolge; paket-hash = SHA-256 ueber den
  Inhalt dieses Pakets. Beide gekuerzt auf --hash-len.
  Pakete (optional, seal/create --max-size N): Teilung an Zeilengrenzen,
  jedes Paket hoechstens N Zeichen inkl. Kopfzeile; Dateien
  <name>.1.ppatch ... <name>.n.ppatch. Die Befehlsliste steht vorne, die
  Daten folgen; ein Datenblock darf ueber Paketgrenzen weiterlaufen.
  check/apply/show nehmen ein beliebiges Paket; die uebrigen werden im
  selben Verzeichnis gesucht (gleicher Name, sonst gleiche Kennung und
  gleicher patch-hash). Fehlt ein Paket oder ist eines beschaedigt ->
  Abbruch, es wird nichts geaendert.
  Mehrere Teile duerfen hintereinander in EINER Datei stehen. Text vor
  der ersten Kopfzeile und Code-Zaeune (```) werden ignoriert; bei
  Entwuerfen beendet ein Code-Zaun ausserhalb eines Datenblocks den Teil
  (folgender Chat-Text bis zur naechsten Kopfzeile entfaellt). Steht ein
  Teil in einem Code-Zaun (Zeile davor beginnt mit ```), endet er am
  schliessenden Zaun - auch mitten in einem Datenblock, der im naechsten
  Teil weiterlaeuft; der oeffnende Zaun des naechsten Teils und Chat-Text
  dazwischen gehoeren nicht dazu.
  Eine Kopfzeile mit fremder Kennung innerhalb eines Datenblocks (oder in
  einem Folgepaket) ist Inhalt - Patches koennen so Dateien uebertragen,
  die selbst Patches enthalten. Beim Teilen endet ein Paket nie mit einer
  Leerzeile oder Zaun-Zeile (diese kommen ins naechste Paket).

6.3 Kopfangaben
  TITLE text       Pflicht, Kurzbeschreibung
  DESC text        Beschreibung; mehrere DESC-Zeilen = mehrere Zeilen
  AUTHOR / DATE / GEN    optional (GEN = erzeugende Programmversion)
  USES funktion ...  genutzte Funktionen, die nicht jede Version kennt:
                   flow (Ablaufsteuerung 6.8), z64 (Komprimierung 6.10).
                   Wird vom Programm selbst eingetragen. Kennt eine
                   Version eine genannte Funktion nicht -> klare Meldung
                   "neuere pypatcher-Version verwenden", nichts geschieht.
  REQ id ...       Patches, die vorher angewendet sein muessen
  MATCH state|unit Pruefumfang (Standard file, Abschnitt 4.6)
  DEFAULT profil   Vorgabe-Profil fuer alle Dateien dieses Patches
  STATE B>A        Projektzustand vorher/nachher (MATCH state, seal --state)
  Leerzeilen und Zeilen mit # (ausser der Kopfzeile) sind Kommentare.
  Die Kennung (id) darf Buchstaben, Ziffern, ".", "_", "-" enthalten und
  wird nie zweimal angewendet.

6.4 Befehle
  Dateibefehle stehen am Zeilenanfang, Aenderungen eingerueckt unter FILE.
    ADD   pfad [profil] [h=>A] [ind=..] [nl=..] [eof=0] @N | src=datei
    DEL   pfad [profil] [h=B]
    REP   pfad [profil] [h=B>A] [ind=..] [nl=..] [eof=0] @N | src=datei
    MOVE  pfad ziel [profil] [h=B>A]
    COPY  pfad ziel [profil] [h=B>A]
    FILE  pfad [profil] [h=B>A] [ind=..]           Datei bearbeiten:
      UNIT  einheit [after=pfad] [u=B>A] @N              Einheit ersetzen
      UADD  [einheit] position [u=>A] @N                 Einheit einfuegen
      UDEL  einheit [u=B]                                Einheit loeschen
      UCOPY quelle position [as=name] [s=Q] [u=>A]       Einheit kopieren
      UMOVE einheit position [u=B>A]                     verschieben (Datei)
      UMOVE einheit to=datei id=M [u=B]                  verschieben: Quelle
      UMOVE quelle position id=M [s=Q] [u=>A]            verschieben: Ziel
      TEXT  [scope=einheit] [u=B>A] @alt @neu            Textblock ersetzen
      TINS  before|after [scope=..] [u=B>A] @anker @neu  Text einfuegen
      TDEL  [scope=..] [u=B>A] @alt                      Textblock loeschen
  Schluessel:
    h=B>A   Datei-Hash vorher>nachher (eine Seite darf fehlen: h=>A, h=B)
    u=B>A   Einheiten-Hash; s=Q Hash der Quell-Einheit
    t=B>A   Text-Hash der Datei, c=B>A Datei-Zwischenstand je Aenderung
            (nur Pruefstufe full)
    after=  Pfad der Einheit nach UNIT (wenn umbenannt)
    ind=4 | ind=tab   layout (6.1);  nl=lf|crlf|cr;  eof=0 = Datei endet
            ohne Zeilenumbruch;  src=datei nur im Entwurf (6.7)
  Profil-Kurzform: py | txt | raw, Abweichungen von den Vorgaben mit
  Komma, z.B. py,comments=keep oder txt,whitespace=keep,eol=keep.
  Ohne Profilangabe gilt DEFAULT bzw. die Vorgabe je Dateiendung.
  Pfade mit Leerzeichen stehen in "...". Positionen: Abschnitt 7.5.
  Hashes: Hex, gekuerzt (Standard 16 Zeichen, mindestens 8, --hash-len).

6.5 Datenbloecke
  @N <anzahl> [lit|b64]   gefolgt von genau <anzahl> Zeilen (so schreibt
                          das Programm; kein Escaping, keine Endmarke)
  @N .                    Zeilen bis zur Zeile "@." (fuer handgeschriebene
                          Entwuerfe, kein Zaehlen noetig)
  @0 <anzahl> z64        Sammelblock: alle Datenbloecke komprimiert (6.10)
  Unbekannte Kennungen -> Meldung "neuere Version verwenden".
  lit = Zeilen exakt wie in der Datei (6.1); b64 = Binaerinhalt (mode raw)
  als Base64 mit 76 Zeichen je Zeile.

6.6 Pruefstufen (seal/create --verify)
  min   nur Datei-Hashes vorher/nachher (h=) - fuer einfache Aenderungen
  std   zusaetzlich Funktions-Hashes (u=, s=) bei Einheiten und scope
        (Standard)
  full  zusaetzlich Datei-Zwischenstand je Aenderung (c=) und exakter
        Text (t=, Voraussetzung fuer apply --exact)
  Beim Anwenden wird geprueft, was im Patch steht; was fehlt, wird nicht
  geprueft (Hinweis, wenn eine Datei gar keinen Datei-Hash hat). Such-
  bloecke (alt/anker) werden immer inhaltlich gesucht und muessen
  eindeutig sein; die Funktion wird ueber die Normalform (Abschnitt 5)
  gewaehrleistet.

6.7 Was nicht im Patch steht
  - Alter Code ersetzter/geloeschter Einheiten und Dateien: den erwarteten
    Ausgangsstand belegt der Hash, den Rollback die Sicherung im Ziel
    (Abschnitt 11). Alter Text steht nur dort, wo er als Suchtext noetig
    ist (TEXT, TINS, TDEL).
  - Inhalt kopierter/verschobener Einheiten: er kommt aus der Quelle,
    abgesichert durch deren Hash (s=).
  Patches fuehren von Version zu Version: ein Patch setzt den passenden
  Ausgangsstand voraus.

6.8 Ablaufsteuerung
  Steuerbefehle stehen zwischen den Dateibefehlen (Einrueckung beliebig):
    PRINT text                  Hinweis ausgeben; ${var} wird ersetzt
    INPUT var ["Frage"] [choices=a,b,c] [default=a]
                                Antwort abfragen (interaktiv, --set
                                var=wert oder default bei -y/ohne Terminal)
    IF bedingung / ELIF bedingung / ELSE / END
                                Bedingung: var == wert | var != wert |
                                var in a,b,c | var (nicht leer, nicht
                                nein/no/0/false)
    LABEL name / GOTO name      Sprung (auch Schleifen, z.B. mit INPUT)
    SET var wert                Variable setzen (${var} moeglich)
    EXIT [grund]                Abbruch ohne jede Aenderung
  Aenderungszeilen (UNIT, TEXT ...) nach einem Steuerbefehl gehoeren zur
  zuletzt genannten Datei (IF/ELSE innerhalb eines FILE).
  Ablauf: Zuerst werden alle Fragen beantwortet und die Zweige bestimmt;
  das Ergebnis ist eine Liste von Dateibefehlen. Erst diese wird geprueft
  und atomar angewendet - eine Entscheidung kann nie ein halb gepatchtes
  Projekt hinterlassen. Die Antworten stehen im Journal (history.json).
  Grenzen: hoechstens 10000 Schritte (Endlosschleife -> Abbruch); ein
  Dateibefehl wird hoechstens einmal ausgefuehrt.
  seal mit Ablaufsteuerung spielt jeden moeglichen Ablauf (jede
  Kombination der choices, hoechstens 64) im Speicher durch; Hashes, die
  in allen Ablaeufen gleich sind, werden eingetragen, ablaufabhaengige
  entfallen (Hinweis). INPUT, das in IF verwendet wird, braucht dafuer
  choices. STATE ist mit Ablaufsteuerung nicht moeglich.

6.9 Entwuerfe aus dem Chat (KI-Nutzung)
  Eine KI ohne Dateizugriff kann keine Hashes berechnen. Sie liefert
  deshalb Entwuerfe, ggf. in Teilen ueber mehrere Nachrichten:
    #PPATCH 1 <id> 1/?    ...    #PPATCH 1 <id> 3/3
  (Gesamtzahl erst im letzten Teil). Der Nutzer kopiert alle Teile in eine
  Datei und ruft "patcher.py run DATEI -p PROJEKT" auf.
  run prueft den Entwurf inhaltlich gegen das Zielprojekt: Einheiten
  muessen existieren und eindeutig sein, Suchbloecke genau einmal
  vorkommen, das Ergebnis muss gueltige Syntax haben (Python/JS/CSS/
  XML). Dann Vorschau, Rueckfrage, Sicherung, atomares Schreiben;
  Rollback wie immer. Versiegelte Patches prueft run ueber die Hashes.
  Konfliktanzeige (0.0.2): wird ein Suchblock nicht gefunden, zeigt die
  Meldung die aehnlichste Stelle im Suchbereich als Diff (- Patch,
  + Datei; ab 50 % Aehnlichkeit, ohne Einrueckung verglichen, hoechstens
  16 Zeilen) bzw. den Hinweis, dass nur die Einrueckung abweicht. Bei
  unbekannten Einheiten nennt sie aehnliche oder die vorhandenen
  Einheiten. Die Meldung ist so gefasst, dass der Nutzer sie unveraendert
  an die KI zurueckgeben kann.
  Die Anleitung fuer die KI steht in ki-prompt.txt (wird getestet);
  ki-beispiele.txt enthaelt durchgespielte Auftraege mit Antworten fuer
  Python, JS/CSS, HTML, JSON, C und eine Antwort ueber zwei Nachrichten
  (alle am Beispielprojekt examples/ki/projekt getestet).
  Kann die KI Code ausfuehren, nutzt sie pypatcher selbst (Einzeldatei
  patcher.pyz, "bundle"; zu Beginn einmal mit dem Projekt anfordern,
  Hilfe selbst mit -h nachsehen): Projekt einlesen, Entwurf schreiben oder eine
  Kopie bearbeiten und "create" nutzen, mit "run -n" selbst pruefen,
  versiegeln und als Datei liefern; nur ohne Download als Text, bei
  Zeichengrenzen mit "pack --compress --max-size N". Dem Nutzer nennt
  sie je Patch genau einen Befehl (run ... -y -q --test "..."), der mit
  einer Zeile antwortet.

6.10 Komprimierung (optional)
  seal/create/pack --compress: alle Datenbloecke werden gemeinsam mit
  zlib (Stufe 9) komprimiert und als Base64 (76 Zeichen je Zeile) in
  einem Sammelblock "@0 <n> z64" abgelegt; Kopfangabe "USES z64".
  - Die Befehlsliste bleibt lesbar; show stellt die Daten entpackt dar.
  - Nur wenn es kleiner wird (sonst bleibt der Patch unkomprimiert).
  - An echten Patches: 53-57 % weniger Zeichen.
  - Base64 statt Base85: kaum groesser (2-3 %), aber ohne Zeichen, die in
    Chats/Markdown stoeren (` @ # *).
  - Patch- und Paket-Hashes gelten fuer den gespeicherten (komprimierten)
    Text; Datei- und Funktions-Hashes bleiben unveraendert.
  - Zweck: Zeichengrenzen bei der Uebertragung. Ausgabe-Tokens einer KI
    spart es kaum (Base64 ist fuer Sprachmodelle teuer); Tokens spart vor
    allem die Lieferung als Datei und knappe Befehle (UNIT/TEXT statt REP).
  Weitere Kodierungen koennen spaeter als neue Kennung hinzukommen.


--------------------------------------------------------------------------------
 7. AENDERUNGEN (changes) UND EINHEITEN
--------------------------------------------------------------------------------
7.1 Uebersicht aller Patch-Befehle
  Dateiebene (Feld "action" im Dateieintrag):
    add        neue Datei anlegen (Ziel darf nicht existieren)
    delete     Datei loeschen
    replace    ganze Datei austauschen
    move       Datei verschieben/umbenennen ("to")
    copy       Datei kopieren ("to")
    modify     Datei bearbeiten -> Liste "changes" (unten)

  Einheiten (action = modify, nur Modi mit Einheiten-Adapter, erste
  Version: python):
    replace_unit   Einheit ersetzen (neuer Inhalt). Umbenennen einer
                   Funktion = replace_unit mit neuem Namen im new-Block.
    add_unit       neue Einheit einfuegen ("position", Abschnitt 7.5)
    (0.0.2) Der new-Block von add_unit/replace_unit darf mehrere
    aufeinanderfolgende Einheiten derselben Ebene enthalten (z.B. drei
    neue Funktionen, oder Funktion + neue Hilfsfunktion); Code ausserhalb
    von Einheiten ist nicht erlaubt. Geprueft wird dann ueber die Hashes
    aller Einheiten (u=), ohne Einheitennamen.
    delete_unit    Einheit entfernen
    copy_unit      Einheit kopieren - in derselben oder aus einer anderen
                   Datei (Abschnitt 7.4)
    move_unit      Einheit verschieben - innerhalb der Datei oder in eine
                   andere Datei (Abschnitt 7.4)

  Text (action = modify, alle Textmodi):
    replace_text   Textblock ersetzen
    insert_text    Text vor/nach einem Anker einfuegen
                   ("anchor": [Zeilen], "position": "before"|"after")
    delete_text    Textblock entfernen
    Der Block bzw. Anker muss GENAU EINMAL vorkommen, sonst Konflikt.
    Suche: zeilenweise; relative Einrueckung exakt (Grundtiefe = Tiefe
    der Zeile, an der der Block beginnt); bei whitespace=ignore zaehlen
    Leerzeichen/Tabs am Zeilenende und reine Leerraum-Zeilen nicht.
    Optional "scope": "<unit>" - gesucht wird nur innerhalb dieser
    Einheit (z.B. wenige Zeilen in einer grossen Funktion aendern).
    Geprueft werden dann zusaetzlich unit_hash_before/after der Einheit.

  Zeilennummern werden bewusst nicht verwendet (zu fehleranfaellig).

7.2 Unit-Adressierung (adapterabhaengig)
  Innerhalb des Dateieintrags: nur der Unit-Pfad. Verweis auf eine
  andere Datei (copy/move): "pfad/datei.py::Klasse.methode".
  Python:
    name                 Funktion/Klasse auf oberster Ebene
    Klasse.methode       Methode
    aeussere.innere      verschachtelte Funktion
    name#2               zweite Definition gleichen Namens
                         (z.B. @property und @x.setter)
    @header              Kopf der Datei
    @imports             zusammenhaengende Imports am Modulanfang (0.0.2)
    LIMIT, Klasse.port   Zuweisung mit genau einem Namen als Ziel auf
                         oberster Ebene oder in einer Klasse (0.0.2):
                         X = ..., X: int = ..., X: int (dataclass-Feld);
                         nicht: a = b = 1, a, b = ..., x += 1, self.x = ...
  JavaScript:
    name                 function name / class name /
                         const|let|var name = function|(..) => {..}|class
    Klasse.methode       Methode, auch #privat, get/set (name#1, name#2),
                         Feld mit Funktion: name = (..) => {..}
    aussen.innen         Funktion in einer Funktion/Methode (0.0.2), auch
                         const innen = (..) => {..}
    api, api.load        Objekt in const/let/var und seine Methoden (0.0.2):
                         load(..) {..}, async/get/set, name: function ..,
                         name: (..) => {..}; api.sub.ping fuer Methoden
                         verschachtelter Objekte (name: {..}). Einfache
                         Werte (base: "/api") sind keine Einheiten.
                         Kommas zwischen Eintraegen setzt das Programm beim
                         Einfuegen/Ersetzen selbst; ein Komma direkt hinter
                         "}" gehoert zur Einheit. start-of:/end-of: gehen
                         bei Klassen und Objekten.
  TypeScript/TSX/JSX (0.0.3) - zusaetzlich zu JavaScript:
    User, Color, Id      interface, enum (auch const enum), type-Alias
                         (Ende an ";" oder wenn die naechste Zeile den Typ
                         nicht fortsetzt); deren Mitglieder sind keine
                         Einheiten (Textbefehle mit scope=User)
    Utils.Strings.upper  namespace/module mit ihren Funktionen/Klassen
    Klasse.methode       auch mit Modifikatoren, Generics, Rueckgabetyp,
                         Dekoratoren (@HostListener(..) gehoert dazu);
                         Methoden ohne Rumpf (abstract, Ueberladungs-
                         Signaturen) sind keine Einheiten
  CSS/SCSS:
    .btn:hover           Regel ueber ihren Selektor (Leerraum wie in der
                         Normalform: einfach, keiner neben ",")
    @media (max-width: 600px)/.btn    verschachtelt, Trenner "/"
    .btn{2}              zweite Regel mit gleichem Selektor
    Im Patch stehen Adressen mit Leerzeichen in "...".
    UCOPY as= ersetzt den Selektor (er muss mit "{" in einer Zeile stehen).
  HTML/XML (robust statt kurz):
    #nav                 Element mit id (bevorzugt)
    #main/section.intro/div.card[3]
                         Pfad ab dem naechsten Element mit id (sonst ab
                         der Wurzel): Tag + Klassen (sortiert) + Nummer
                         unter gleichartigen Geschwistern, [1] entfaellt
                         wenn eindeutig
    html/head/script[2]  <script>/<style> sind ganze Einheiten
    Einheit ist jedes Element mit End-Tag (bzw. leeres/void-Element),
    das zeilenweise abgrenzbar ist; Elemente ohne ausdrueckliches
    End-Tag (z.B. <li> ohne </li>) sind keine Einheiten. Kommentarzeilen
    direkt darueber gehoeren dazu. start-of:/end-of: verlangen, dass
    Start- und End-Tag jeweils allein in ihrer Zeile stehen.
    UCOPY as= wird nicht unterstuetzt.
  C/C++:
    add                  Funktion; struct/union/enum/class ueber ihren Namen
    app::Box::get        Namespace/Klasse/Methode wie im Code mit "::";
                         auch Definitionen ausserhalb: "Box::get" (Template-
                         Argumente entfallen: Box<int>::get -> Box::get)
    operator==, ~Box     Operatoren, Destruktoren
    Kommentarzeilen direkt darueber gehoeren dazu; Felder, Deklarationen
    ohne Rumpf und Initialisierungen sind keine Einheiten.
  Java (0.0.3):
    NoteStore            Klasse, interface, enum, record, @interface
    NoteStore.add        Methode; Konstruktoren heissen wie die Klasse
                         (NoteStore.NoteStore), Ueberladungen name#1,
                         name#2 in der Reihenfolge der Datei
    NoteStore.Entry.size innere Klassen/Enums mit "." verschachtelt
    Annotationen (@Override ...) und Javadoc/Kommentare direkt darueber
    gehoeren zur Einheit. Keine Einheiten: Felder, static-/Instanz-
    Initialisierer, anonyme Klassen und Lambdas (liegen in Methoden),
    Methoden ohne Rumpf (abstract, interface).
  JSON:
    server/port          Eintrag ueber den Pfad (Schluessel, Listen-Index)
    plugins/0/name       "/" und "~" in Schluesseln als ~1 bzw. ~0
    UCOPY as= benennt den Schluessel um.
  Nicht gefunden oder nicht eindeutig -> Konflikt, Abbruch.
  Einheiten muessen zeilenweise abgrenzbar sein (Anfang am Zeilenanfang,
  Ende am Zeilenende); was sich eine Zeile mit anderem Code teilt, ist
  keine Einheit und wird ueber Textbefehle geaendert.

7.3 Umfang einer Einheit (Python-Adapter, sinngemaess fuer andere)
  Der Umfang bestimmt, welcher Text beim Ersetzen/Loeschen/Verschieben
  mitgenommen wird. In den Hash fliesst davon nur die Normalform ein.
  @header     Beginnt in Zeile 1 und umfasst, sofern vorhanden:
                - Shebang ("#!...")             -> funktional
                - Encoding-Zeile                -> funktional
                - zusammenhaengender Kommentarblock am Dateianfang
                                                -> nach Profil "comments"
                - Modul-Docstring               -> funktional (E11)
              Endet vor der ersten Zeile, die nicht dazugehoert.
              Imports gehoeren NICHT zum Header.
  @imports    Die Import-Anweisungen am Modulanfang (nach @header), solange
              sie ohne andere Anweisung aufeinander folgen, inkl.
              Kommentarzeilen direkt darueber. Aendern: UNIT @imports
              mit dem kompletten neuen Import-Block.
  Zuweisung:  Kommentarzeilen direkt darueber + Anweisung (auch ueber
              mehrere Zeilen).
  Funktion/Klasse/Methode:
                - zusammenhaengende Kommentarzeilen DIREKT darueber
                  (ohne Leerzeile dazwischen, gleiche Einrueckung)
                - alle Decorators
                - Definition bis Ende des Rumpfs (ast: end_lineno)
                - Einrueckung jeder Anweisungszeile exakt (E13)
              Vorrang: Was zum @header gehoert, gehoert nie zu einer
              Funktion - auch wenn die Funktion ohne Leerzeile folgt.
  Leerzeilen zwischen Einheiten gehoeren zu keiner Einheit; add_unit,
  delete_unit, copy_unit und move_unit halten den ueblichen Abstand ein:
    Einfuegen : 2 Leerzeilen auf oberster Ebene, 1 Leerzeile in Klassen
                (vor und nach dem Block; vorhandene Leerzeilen zaehlen
                mit; direkt nach einer Zeile mit ":" keine). Zwischen
                einer eingefuegten Zuweisung und einer benachbarten
                Zuweisung/Import gleicher Tiefe keine (0.0.2).
    Entfernen : von den Leerzeilen davor und danach bleibt die groessere
                Anzahl stehen.
  Der Text-Hash aendert sich dadurch, der Funktions-Hash nicht.

7.4 Kopieren und Verschieben von Einheiten
  copy_unit (im Dateieintrag der ZIELdatei):
    "from"      Quelle: "unit" (gleiche Datei) oder "pfad::unit"
    "position"  Zielstelle (7.5)
    "as"        optional: neuer Name der Kopie (nur der Name in der
                def/class-Zeile wird geaendert)
    Inhalt      kommt beim Anwenden aus der Quelle (steht nicht im
                Patch); abgesichert durch source_unit_hash (s=).
    Pruefung: source_unit_hash == Hash der Quelle zum Zeitpunkt der
    Ausfuehrung; unit_hash_after der Kopie; Datei-Hash-Kette.
    Die Quelle bleibt unveraendert.
  move_unit innerhalb einer Datei:
    "unit", "position" - Einheit wird an die neue Stelle verschoben.
    Pruefung: unit_hash_before/after (Inhalt gleich, nur Tiefe kann sich
    aendern, z.B. Methode -> Funktion) und Datei-Hash-Kette.
  move_unit in eine andere Datei (zwei zusammengehoerige Aenderungen):
    Zieldatei  : UMOVE a.py::X end id=m1          fuegt ein (zuerst)
    Quelldatei : UMOVE X to=b.py id=m1            entfernt die Einheit
    Beide Haelften muessen im Patch vorhanden sein (gleiche move_id),
    sonst ist der Patch ungueltig. seal ordnet sie so, dass zuerst
    eingefuegt und dann entfernt wird; da alles im Speicher geschieht,
    ist die Reihenfolge der Dateien sonst beliebig.
  Hinweis: Verschieben/Kopieren kann die Bedeutung aendern (z.B. Methode
  mit self auf Modulebene). Geprueft werden Syntax (validate) und
  Hashes; die fachliche Richtigkeit liegt beim Ersteller des Patches.

7.5 Positionen (add_unit, copy_unit, move_unit)
  "after:<unit>"      direkt nach der Einheit
  "before:<unit>"     direkt vor der Einheit (vor deren Kommentaren/
                      Decorators)
  "start"             direkt nach @header (und nach dem Import-Block)
  "end"               Dateiende
  "start-of:<klasse>" erste Stelle im Klassenrumpf (nach Docstring)
  "end-of:<klasse>"   letzte Stelle im Klassenrumpf

7.6 Einrueckung je Befehl (Grundtiefe; Einheit pro Ebene aus der Datei)
  add / replace (Datei)     Grundtiefe 0; Einheit aus layout (Pflicht,
                            wenn der Inhalt Einrueckung enthaelt)
  replace_unit              Tiefe der bisherigen Einheit
  add_unit, copy_unit,      after:/before:X  -> Tiefe von X
  move_unit                 start-of:/end-of:K -> Tiefe des Rumpfs von K
                            start / end      -> 0
  delete_unit, delete_text  - (nichts einzufuegen)
  replace_text              Tiefe der ersten Zeile des gefundenen Blocks
  insert_text               Tiefe der Ankerzeile
                            (relativ dazu: "\t" = eine Ebene tiefer)
  Fuer old/anchor gilt dieselbe Darstellung; gesucht wird ueber die
  Normalform, dabei muessen die relativen Ebenen uebereinstimmen.

 9. ENTWURF (fuer "seal")
--------------------------------------------------------------------------------
Ein Entwurf ist eine Patchdatei ohne Hashes (Kopfzeile "#PPATCH 1 <id>"),
von Hand geschrieben:

  #PPATCH 1 0003-udf
  TITLE is_udf beschleunigen
  FILE src/convert.py
    UNIT is_udf @1
  @1 .
  def is_udf(path):
  	return pruefe(path, "UDF")
  @.

"patcher.py seal entwurf.ppatch --base PROJEKT -o 0003-udf.ppatch"
liest den Ist-Stand aus PROJEKT, ergaenzt Profile, layout als Check
(aus der Datei erkannt, ausser --no-layout) und die Hashes der gewaehlten
Pruefstufe, prueft die Einrueckung (python), wendet den Patch probeweise
im Speicher an (inkl. Syntaxpruefung) und schreibt ihn - auf Wunsch in
Pakete geteilt (--max-size). Aendert ein Entwurf nur Kommentare oder
unwichtigen Leerraum (Funktions-Hash vorher == nachher), weist seal
darauf hin.

Zusaetzlich im Entwurf:
  src=datei   bei ADD/REP: Inhalt aus dieser Datei lesen (relativ zum
              Verzeichnis des Entwurfs). Binaerdateien werden mode raw.
  --state     traegt STATE ein (MATCH state).
Beispiel: examples/entwurf-beispiel.ppatch
Ein Entwurf kann statt mit seal auch direkt mit "run" gegen das
Zielprojekt geprueft und angewendet werden (6.9).

10. ARBEITSABLAUF
--------------------------------------------------------------------------------
  Entwicklungsumgebung                       Zielumgebung
  --------------------                       ------------
  (a) automatisch:                           patcher.py doctor (spaeter)
      patcher.py create ALT NEU -o p.ppatch  patcher.py init     (einmalig)
  (b) von Hand:                              patcher.py check p.ppatch
      Entwurf schreiben ->                   patcher.py apply p.ppatch
      patcher.py seal entwurf --base P       patcher.py status / verify
                                             patcher.py rollback (bei Bedarf)
            ---- p.ppatch (ggf. Pakete) uebertragen ---->

  "create" vergleicht zwei Staende. Profile kommen aus
  --compare, .patcher/config.json von ALT oder den Vorgaben je
  Dateiendung; ignoriert wird wie bei init (Muster von ALT).
  Hashes werden NIE von Hand geschrieben.

  Dateien:
    nur in NEU          add (Inhalt aus NEU); gleicher Inhalt wie eine
                        nur in ALT vorhandene Datei -> move, wie eine
                        unveraenderte Datei -> copy
    nur in ALT          delete
    in beiden, anders   modify, Binaerdateien replace
  Innerhalb einer Datei (modify):
    1. Einheiten (mode python, --level unit): Kopf geaendert ->
       replace_unit @header. Einheiten gleichen Namens werden verglichen;
       ist nur der Inhalt von Kind-Einheiten anders (Methoden einer
       Klasse), wird in die Kinder abgestiegen, sonst replace_unit.
       Weggefallene -> delete_unit, neue -> add_unit (Position nach dem
       vorherigen Geschwister, sonst vor dem naechsten, sonst start-of
       der Klasse bzw. Dateiende). Geaenderte Reihenfolge -> keine
       Einheiten-Befehle fuer diese Ebene (Text uebernimmt).
    2. Dateiuebergreifend: in A geloeschte und in B neue Einheit mit
       gleichem Inhalt -> move_unit-Paar (move_id; B steht vor A).
       Neue Einheit gleich einer unveraenderten Einheit -> copy_unit.
    3. Verbleibende Unterschiede (Imports, Code auf Modulebene,
       Leerzeilen, Textdateien) -> replace_text/insert_text/delete_text
       mit so viel Kontext, dass der Block eindeutig ist; von unten nach
       oben angeordnet.
    Datei mit anderen Zeilenenden/BOM/Dateiende-Umbruch als vorher ->
    replace. --level text: nur Schritt 3; --level file: nur ganze Dateien.
  Platz: Sind die Einzelaenderungen einer Datei groesser als die ganze
  neue Datei, wird die ganze Datei aufgenommen (REP).
  Exaktheit: Der erzeugte Patch wird im Speicher auf ALT angewendet und
  jede Datei Byte fuer Byte mit NEU verglichen. Passt eine Datei nicht,
  wird sie als ganze Datei (replace) aufgenommen. Ein mit create
  erzeugter Patch fuehrt damit immer exakt zum Stand NEU.
  Rein kosmetisch veraenderte Dateien (gleicher Funktions-Hash) werden
  nur gemeldet, mit "--include-cosmetic" uebernommen.

11. JOURNAL / ROLLBACK
--------------------------------------------------------------------------------
Verzeichnis ".patcher/" in der Projektwurzel:

  .patcher/
    config.json          Vorgabe-Profile fuer create/seal, Mindestprofile
    state.json           je Datei: Profil, hash, text_hash; Zustands-Hash
    history.json         Stapel der angewendeten Patches: ID, Zeitpunkt,
                         patch_hash, Zustand vorher/nachher
    patches/<ID>.ppatch  Kopie jedes angewendeten Patches (einteilig)
    backups/<ID>/files/  exakte Originaldateien vor dem Patch
    backups/<ID>/meta.json     welche Dateien vorher existierten
    txn.json             nur waehrend einer laufenden Transaktion
  history.json enthaelt je Patch und Datei einen Fingerabdruck vorher
  und nachher (Profil, hash, text_hash, Hash der rohen Bytes).

Rollback:
  - Standard: nur der zuletzt angewendete Patch (LIFO).
  - "rollback --to <ID>": alle Patches nach <ID>, neuester zuerst.
  - Ablauf: Pruefung, dass der Ist-Stand gemaess Profil dem Stand nach
    dem Patch entspricht (hash_after). Dann werden die exakten
    Originaldateien aus backups/<ID>/ zurueckgeschrieben (inkl.
    Kommentare und Formatierung). Weicht der Ist-Stand ab -> Abbruch.
    Durch den Patch angelegte Dateien werden entfernt, dadurch leer
    gewordene Verzeichnisse ebenfalls. Danach werden Sicherung und
    Patch-Kopie geloescht; der Patch kann erneut angewendet werden.
  - "invert" (spaeter): erzeugt aus Patch und Sicherung einen
    eigenstaendigen Rueckwaerts-Patch, z.B. zur Weitergabe. Der Patch
    allein enthaelt keinen alten Code (E19).


--------------------------------------------------------------------------------
12. ATOMARITAET / FEHLERSICHERHEIT
--------------------------------------------------------------------------------
apply laeuft in drei Phasen:
  1. PRUEFEN    Patch-/Paket-Hashes, Vollstaendigkeit, REQ, doppelte ID,
                Gueltigkeit der Vergleichsprofile, Mindestprofile,
                alle enthaltenen Datei- und Unit-Hashes. Alle neuen
                Dateiinhalte werden im Speicher berechnet und geprueft.
                -> Fehler hier: nichts wurde veraendert.
  2. SICHERN    Betroffene Dateien nach .patcher/backups/<ID>/ kopieren,
                txn.json anlegen.
  3. SCHREIBEN  Jede Datei in eine Temp-Datei im selben Verzeichnis
                schreiben, dann os.replace() (atomar je Datei). Danach
                history.json und state.json aktualisieren, txn.json
                loeschen.
Schlaegt das Schreiben fehl, wird sofort aus der Sicherung
wiederhergestellt. Findet ein Programmstart eine vorhandene txn.json
(Absturz), verweigern apply/rollback die Arbeit; "recover" bereinigt:
  - apply unterbrochen, Patch noch nicht im Journal -> Ausgangsstand aus
    backups/<ID>/ wiederherstellen
  - apply unterbrochen, Patch bereits im Journal -> nur txn.json loeschen
  - rollback unterbrochen -> Rollback zu Ende fuehren
Dateirechte bleiben erhalten; neue Dateien erhalten 0666 minus umask.
Wird eine .py-Datei geschrieben, wiederhergestellt oder geloescht, wird
ihr Bytecode in __pycache__ entfernt (Python erkennt veralteten Bytecode
nur an Aenderungszeit in Sekunden und Groesse der Quelle).
Die Syntax einer Python-Datei wird nach ihrer letzten Aenderung geprueft;
Zwischenstaende von Textaenderungen duerfen ungueltig sein.

13. BEFEHLE (KOMMANDOZEILE)

  Befehl    Ab       Aufruf / Zweck
  --------  -------  ---------------------------------------------------
  init      0.0.1    patcher.py init [-p PROJEKT] [--force]
                     Journal anlegen, Ist-Stand als Ausgangszustand;
                     --force (0.0.2): neu anlegen, nur ohne angewendete

  seal      0.0.1    patcher.py seal ENTWURF --base PROJEKT -o DATEI

  apply     0.0.1    patcher.py apply PATCH [-p PROJEKT]

  pack      0.0.1    patcher.py pack PATCH -o DATEI [--compress] [--max-size N]
                     Patch/Entwurf umpacken (komprimieren, entpacken,

  bundle    0.0.1    patcher.py bundle [-o patcher.pyz]
                     pypatcher als eine Datei (zipapp, ca. 70 KB), z.B.

  run       0.0.1    patcher.py run PATCH [-p PROJEKT] [-n] [--set V=W ...]
                     [TESTS]
                     Entwurf (z.B. von einer KI) oder Patch direkt
                     pruefen und anwenden; -n = Probelauf (6.9)
  rollback  0.0.1    patcher.py rollback [-p PROJEKT] [--to ID]
  recover   0.0.1    patcher.py recover [-p PROJEKT]
  create    0.0.1    patcher.py create ALT NEU -o DATEI --id ID --title T
                     [--description D] [--author A] [--requires ID ...]
                     [--compare P] [--level unit|text|file]
                     [--include-cosmetic] [--no-layout] [AUSGABE]
                     Patch aus zwei Staenden (Abschnitt 10); erkennt
                     verschobene/kopierte Einheiten und Dateien.
  doctor    spaeter  patcher.py doctor [-p PROJEKT]
                     Python-Version, Betriebssystem, Schreibrechte,
                     Encoding, Zeilenenden, Einrueckungsart, parsebar
  canon     spaeter  patcher.py canon DATEI [--unit U] [--compare P]
                     Normalform anzeigen (Diagnose)
  invert    spaeter  patcher.py invert PATCH -o DATEI
                     Rueckwaerts-Patch erzeugen

  Alle Patch-Befehle aus Abschnitt 7.1 (inkl. copy/move, delete_text,
  scope) sind ab 0.0.1 enthalten.
  Allgemein: -v (ausfuehrlich, bei internen Fehlern mit Details),
             -q (still), -y (keine Rueckfragen; ohne Terminal wird
             ohnehin nicht gefragt), --allow-mixed-eol, --version,
             --color auto|always|never (0.0.2): gruen = Erfolg, rot =
             Fehler/Abbruch, gelb = Warnung, cyan = Hinweis; in
             Konfliktmeldungen "- Patch" rot, "+ Datei" gruen. auto =
             nur wenn die Ausgabe ein Terminal ist und weder NO_COLOR
             gesetzt noch TERM=dumb ist (Windows: ANSI wird in der
             Konsole eingeschaltet, sonst ohne Farbe). In Dateien und
             Pipes (Logs, Weitergabe an eine KI) nie Steuerzeichen.
  --compare P: Profil als Kurzform, z.B. "python" oder
               "text,whitespace=keep" oder "raw".
  AUSGABE (seal, create): --verify min|std|full (Pruefstufe, 6.6;
               Standard std), --hash-len N (8-64, Standard 16),
               --max-size N (Pakete mit hoechstens N Zeichen, 6.2),
               --compress (Datenbloecke komprimieren, 6.10).
  PATCH (show, check, apply, run): Patchdatei oder ein beliebiges Paket;
               Teile duerfen in einer Datei stehen.
  --set V=W (check, apply, run): Antwort auf INPUT vorgeben (6.8).
  TESTS (apply, run; 0.0.2): ein Befehl je Patch. Nach dem Anwenden
               wird das Journal geprueft (vor den Tests, die Dateien
               anlegen duerfen), dann der Testbefehl im Projekt
               ausgefuehrt, zuletzt eine Ergebniszeile ausgegeben - auch
               mit -q, z.B. "OK 0005-x | 2 Dateien | Journal OK | Tests OK".
               --test BEFEHL     Testbefehl (Shell), Vorgabe: "test" aus
                                 .patcher/config.json
               --no-test         keine Tests, auch nicht aus config.json
               --rollback-on-failure  bei fehlgeschlagenen Tests sofort
                                 zuruecknehmen; sonst bleibt der Patch
                                 zur Untersuchung angewendet. Dauerhaft:
                                 "rollback_on_failure": true in
                                 .patcher/config.json
               Exit-Code 6 bei fehlgeschlagenen Tests, 3 bei Abweichungen
               im Journal. Mit -q erscheint die Ausgabe der Tests nur,
               wenn sie fehlschlagen.

Exit-Codes:

15. GRENZEN / BEWUSSTE NICHT-ZIELE
--------------------------------------------------------------------------------
  - Kein Ersatz fuer git; keine automatische Zusammenfuehrung (Merge).
  - Kein Code-Formatierer: der Patcher formatiert nie um (A9), passt
    insbesondere nie Python-Einrueckung an.
  - Erste Version: Einheiten nur fuer Python; andere Dateien ueber
    Text-Operationen bzw. ganze Datei.
  - Patches bauen aufeinander auf; Rollback in umgekehrter Reihenfolge.
  - Patch-Hash schuetzt gegen Beschaedigung, nicht gegen absichtliche
    Manipulation (dafuer spaeter eine Signatur).
  Offene Punkte: keine.

16. DOKUMENTATIONSREGELN UND VERSIONIERUNG
--------------------------------------------------------------------------------
  readme.txt     Kurzanleitung fuer Anwender (Installation, Befehle,
                 Beispiele). Bei jeder Bedienungsaenderung anpassen.
  changelog.txt  Jede Aenderung mit Version (bzw. "Konzeptphase") und
                 Datum, neueste oben.
  request.txt    Wuensche/Ideen fuer kuenftige Aenderungen mit Status
                 (OFFEN / GEPLANT / IN ARBEIT / ERLEDIGT x.y.z / ABGELEHNT).
  manifest.txt   Diese Datei: vollstaendige Beschreibung. Bei jeder
                 Aenderung an Format, Profilen, Normalformen, Befehlen
                 oder Verhalten anpassen.

  Versionierung:
  - Konzeptphase: keine Versionsnummern.
  - Schema MAJOR.MINOR.PATCH, Beginn mit 0.0.1.
  - Vorabstaende bis zur Freigabe: 0.0.1-pre1, 0.0.1-pre2, ... (aufsteigend).
  - Freigabe: Suffix entfaellt (0.0.1). Danach naechste Version wieder
    mit -pre1 beginnend (z.B. 0.0.2-pre1).
  - Version steht in pypatcher/__init__.py (__version__), wird mit
    --version ausgegeben und in jeden erzeugten Patch eingetragen
    (Kopfangabe "GEN pypatcher 0.0.1").
  - Formatversion ("pypatcher/<n>") und Normalform-Versionen
    ("python/<n>") werden davon unabhaengig gezaehlt.
